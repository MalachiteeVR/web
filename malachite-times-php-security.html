Critical PHP Vulnerabilities Trigger Global Security Alert

Two critical flaws disclosed on October 21 can allow unauthenticated remote code execution on vulnerable PHP installations. The vulnerabilities also became part of the security investigation that led MalachiteVR to take its infrastructure offline.

Technology Desk · October 22, 2026

PHP developers released emergency security updates on October 21, 2026, addressing two critical vulnerabilities tracked as CVE-2026-109618 and CVE-2026-109619. The PHP project rated both vulnerabilities CVSS 4.0 9.2 and warned that they can allow an unauthenticated attacker to achieve remote code execution.

Fixed releases: PHP 8.5.12, 8.4.27, 8.3.36, and 8.2.35. PHP's security team says updating is the only complete solution. PHP 8.1 and older are no longer supported by the PHP project, although some operating-system vendors provide backported fixes.

What makes these vulnerabilities serious?

The first vulnerability, CVE-2026-109618, involves PHP's handling of out-of-memory conditions. Under the vulnerable behavior, an interruption can leave internal request data only partially initialized, after which cleanup code may treat that invalid state as legitimate.

The second, CVE-2026-109619, involves stale internal request state. Memory belonging to a request can be freed while related global state continues to point toward it. A later request handled by the same worker can then encounter that stale state.

In practical terms, both bugs affect the PHP runtime itself rather than being ordinary application-level mistakes. A vulnerable, internet-facing PHP service can therefore present a serious attack surface before the application's own code gets a chance to protect the request.

Who is affected?

The PHP advisory says the risk applies to PHP installations serving web requests, including PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP, and LiteSpeed. PHP's advisory identifies mod_php as the highest-risk configuration because a demonstrated exploit can trigger the vulnerable behavior before application code executes.

Ubuntu also published a security notice confirming that specially crafted network traffic can cause vulnerable PHP installations to crash or execute programs. Security agencies in Europe and Canada likewise urged organizations to identify exposed PHP systems and patch them immediately.

The situation moved quickly

This was not a vulnerability that could comfortably wait for the next maintenance cycle. Palo Alto Networks' Unit 42 reported that it had observed exploitation in the wild and identified more than 22.6 million potentially exposed instances through its telemetry.

The European Commission, ENISA, CERT-EU, Europol EC3, and the EU CSIRTs network advised organizations to take immediate action and prioritize internet-facing PHP systems. The Canadian Centre for Cyber Security likewise recommended immediate updates, isolation where immediate remediation was not possible, and monitoring for signs of compromise.

Why it mattered to MalachiteVR

The disclosure was one of the events that triggered a security review of MalachiteVR infrastructure. That investigation ultimately confirmed that the MalachiteVR Query Server had been compromised.

Because the compromised environment contained sensitive infrastructure information, the response went beyond simply installing a PHP update. MalachiteVR took its infrastructure offline, preserved relevant evidence, rotated exposed credentials and keys, rebuilt affected systems from trusted sources, and brought services back only after the rebuild was complete.

It is important to distinguish the two facts: the PHP vulnerabilities were a critical security issue, while the confirmed MalachiteVR compromise was an incident involving the Query Server. The investigation determined that exposed credentials and infrastructure information had to be treated as compromised, so the response was deliberately broader than a software patch.

The lesson for server operators

For administrators running PHP, the immediate lesson is straightforward: identify every internet-facing PHP installation, determine whether it is running a vulnerable version, and apply the vendor or distribution's fixed packages.

The broader lesson is about incident response. When a vulnerable internet-facing service is suspected of being compromised, patching the software does not automatically prove that the machine is trustworthy again. Logs, authentication records, unexpected processes, files, accounts, and outbound connections can all matter when determining whether an attacker gained access.

When the software is patched but the machine's trust boundary is uncertain, the problem has changed from patch management to incident response.

Where things stand

PHP's emergency releases are available now, and the MalachiteVR infrastructure involved in the incident has been rebuilt and restored. The PHP project continues to recommend immediate updates for affected installations.

Sources: PHP Security Advisory, October 21, 2026; Ubuntu Security Notice USN-8948-1; ENISA joint statement; Canadian Centre for Cyber Security Alert AL26-026; Palo Alto Networks Unit 42 threat brief.
